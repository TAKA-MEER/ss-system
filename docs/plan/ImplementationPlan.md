**「完了」と書かない。**何を根拠にそう言えるかを列に出す。

## 2. 進め方の原則

| # | 原則 | 補足 |
| --- | --- | --- |
| 1 | **実装は codex に投げ、利用枠の上限が来たら opencode に切り替える。窓口は herdr か orca**（いま開いている方を使う） | 体数は固定しない。必要なだけ増やす（下記 §2.1） |
| 2 | **順番は「段階」ではなく「用途」で決める** | 実際の運用で先に要るもの・安全にかかわる穴から埋める（§6）。段階は作業のまとまりで、実施順ではない（th-system で段階順の原則がデモで破れた経緯から） |
| 3 | **検証は必ず実装管理担当（人＋Claude）が自分で行う** | **実装エージェントの「テストが緑」報告は信用しない。**下記 §2.2 |
| 4 | **完成の判定は実行できるコマンドで行う** | 「できたと思う」で先に進まない |

### 2.1 実装エージェントの動かし方（herdr ／ orca ＋ codex ／ opencode）

**1 作業パケット ＝ 1 ブリーフ ＝ 1 エージェント**。並行数は作業の独立性で決める。

**どのエージェントに投げるか**（th-system 2026-10-26 ユーザー決定に揃えた）: **まず codex。利用枠の上限が来たら opencode。**

| 項目 | codex | opencode |
| --- | --- | --- |
| 起動（orca） | `--agent codex` | `--agent opencode` |
| 指示ファイル | リポジトリ直下の `AGENTS.md`（「`CLAUDE.md` を読め」とだけ書いてある） | `CLAUDE.md` |
| 利用枠 | ChatGPT の **無料プラン・30 日単位の枠**。**使い切ると約 1 か月戻らない。th-system・hve-system・fk-system と共有** | 無料枠。上限に達すると idle のまま進まなくなる |
| 枠の確かめ方 | codex の画面で `/status`、または `~/.codex/sessions/` の最新ログの `rate_limits.primary.used_percent` | — |
| 試用状況 | th-system で orca から通した（2026-10-29。実装 1 回＋差し戻し 2 回、各 2〜4 分で枠を 8% 使った）。ss-system では未使用 | th-system・hve-system で実績あり |

**どちらの中で動いているかは環境変数で見分ける。**

```bash
env | grep -E '^(TERM_PROGRAM|ORCA_TERMINAL_HANDLE|HERDR_PANE_ID|HERDR_ENV)='
```

| 見えるもの | いる場所 | 使う手順 |
| --- | --- | --- |
| `TERM_PROGRAM=Orca` ／ `ORCA_TERMINAL_HANDLE=term_…` | **orca** | 下の「orca の場合」 |
| `HERDR_PANE_ID` ／ `HERDR_ENV` | **herdr** | 下の「herdr の場合」。**※変数名は herdr 0.8.2 の実行ファイルから拾ったもので、ペイン内での実在は未確認**（th-system の注記のまま） |
| どちらも無い | 素の端末 | どちらかのコマンド（`orca status` ／ `herdr status`）が通る方を使う |

#### herdr の場合

```bash
herdr tab list                                    # ImplementAgent タブの tab_id を確認
herdr pane split --pane <既存pane> --direction right   # 体を増やすときはペインを分ける
herdr agent list                                  # pane が agent="opencode" として自動検出されたか確認
herdr agent rename <pane_id> <name>               # 名前を付ける（start ではなく rename）
herdr agent prompt <name> "指示書は .briefs/brief-<ID>.md。全文を読み前提誤りを指摘、無ければ最後まで実装"
herdr agent get <name>                            # agent_status を 10 秒間隔でポーリングして監視
```

| 項目 | 決まりごと | 理由 |
| --- | --- | --- |
| ブリーフの置き場 | **`.briefs/`（リポジトリ内・gitignore 済み）** | リポジトリ外に置くと opencode が「外部ディレクトリアクセス許可」で毎ターン止まる |
| 一時ファイル | **`.briefs/tmp/`。`/tmp` を使わせない** | 同上。「Allow always」を選んでもターンを跨いで再発する |
| 既に opencode が動いているペイン | **`agent start` を打たない。`agent rename` だけ**で登録する | `start` はシェルプロンプト待ちを期待するため、動作中のセッションに文字列を打ち込んで壊す |
| 並行させるとき | **片方を `git worktree` に隔離する** | 同じファイルを 2 体が触ると衝突する。`herdr worktree` が helper を持つ |
| 監視 | `herdr agent get` のポーリング | `herdr agent wait --until` は状態の遷移を取りこぼす |
| 承認プロンプト | `herdr agent send-keys <name> Left Left Right Enter` で「Allow always」 | カーソル位置が読めないので左端へ寄せてから 1 つ右 |
| コミット | **細かく切らせる** | **無料枠・クォータで途中で止まる前提。**opencode は上限に達すると idle のまま進まなくなる |
| `git push` | **投げない。実装管理担当が検証してから押す** | — |

#### orca の場合

**ss-system はまだ orca に登録していない**（`~/orca/workspaces/` に無い）。最初に投げるときに登録する。

```bash
orca worktree create --name <n> --no-parent --setup skip --agent codex --json      # worktree 作成と codex 起動を 1 回で（枠切れなら --agent opencode）
git -C <worktreeのpath> branch -m <git ユーザー名>/<n> <種別>/<主題>     # orca はブランチ名を <git ユーザー名>/<n> にする（th-system 2026-10-29 時点）ので付け替える
mkdir -p <worktreeのpath>/.briefs/tmp                    # .briefs は gitignore なので新しい worktree には無い。ブリーフもここに置く
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 60000 --json   # satisfied:true を確かめてから送る
orca terminal send --terminal <handle> --text "指示書は .briefs/brief-<ID>.md。…" --enter --json
orca terminal read --terminal <handle> --limit 60        # 監視。画面に `esc interrupt`（codex は `esc to interrupt`）があれば作業中
orca worktree rm --worktree id:<repoId>::<path> --force --json   # 片付け。フォルダ・ターミナル・ローカルブランチまで消える
```

| 項目 | 決まりごと | 理由 |
| --- | --- | --- |
| `worktree create` | **`--setup skip` を必ず付ける** | repo 設定のセットアップ hook が `pnpm install`（既定で実行）で、リポジトリ直下に `package.json` が無いと失敗する |
| worktree の置き場 | `~/orca/workspaces/ss-system/<n>`（リポジトリの外） | — |
| 投入の確認 | `terminal send` の結果ではなく**画面を読んで**確かめる | opencode は `provider: unsupported` で、ターンが始まったことを orca が証明できない |
| 監視 | `terminal read` を 30 秒間隔で読むスクリプトを Monitor で回す（`esc (to )?interrupt` が 2 回続けて無ければ停止） | ターン終了の通知が無い。**codex の表示は `esc to interrupt` で、`esc interrupt` では拾えない** |
| codex の起動直後 | 「Update available」の選択画面で止まることがある。`--text $'\x1b'` で飛ばす（更新はしない） | グローバルの npm パッケージを黙って入れ替えない |
| codex の権限 | `permissions: YOLO mode` で動き、承認プロンプトは出ない。監視で `permission` を拾うと起動画面のこの行に毎回反応するので拾わない | 範囲はブリーフで縛るしかない |
| 承認プロンプト（opencode） | `orca terminal send --text "" --enter` で既定の「Allow once」が通る。「Allow always」は `CLAUDE.md`「環境の癖」の手順。中断は `--text $'\x1b'` を 2 回 | worktree 外の読み取り（パスの書き間違い・`/tmp`）で出ることが多い |
| 片付けの前 | Docker を使ったなら、残した root 所有ファイルを `chown` で戻しておく | root 所有のファイルが残ると `git worktree remove` が Permission denied で失敗する |

ブリーフ・一時ファイル・コミット・`git push` の決まりごとは herdr の表と同じ。

### 2.2 受け入れ検査（実装管理担当がやること）

**実装は信用してよい。テストは絶対に信用しない。**（th-system で、通るだけで何も検出しないテストが繰り返し出てきた）

1. 試験（使う道具が決まったら、そのコマンドを `CLAUDE.md`「ビルドとテスト」に書く）を**自分で回す**
2. **変異チェックを 1〜2 件は自分で再実行する** — 実装ファイルを `sed` で壊し、該当テストが赤くなるか。
   **Python は毎回 `__pycache__` を消し、`python3 -B -m pytest -p no:cacheprovider` で回す**（同じ秒の中で同じ長さに書き換えて戻すと古い `.pyc` が使われ、赤・緑が入れ替わる。th-system 2026-10-29）。
   エージェント自身の変異は純関数側だけのことが多い。**呼び出し側（CLI の配線・ノード本体）を壊す変異を自分で足す**（th-system 2026-10-29 の codex でも配線の変異が 2 回すり抜けた）
3. `git show <commit>` で差分がブリーフの範囲内かを目視する
4. 起動まで要るものは、起動スモークまで自分で

### 2.3 git の運用（実装管理担当が持つ）

**ブランチ・マージ・push・掃除はすべて実装管理担当の責任。**
実装エージェントは**自分の作業ブランチにコミットするところまで**で、それ以外の git 操作はしない。

| 操作 | 誰が | 備考 |
| --- | --- | --- |
| ブランチを切る | **実装管理担当** | ブリーフを渡す前に切り、エージェントにはブランチ名を伝える |
| コミットする | 実装エージェント | **細かく切らせる**（クォータで途中停止する前提。§2.1） |
| `main` へマージ | **実装管理担当** | §2.2 の受け入れ検査を通してから |
| `git push` | **実装管理担当** | エージェントには投げさせない。**`main` へのコミット（文書の直接コミット・マージ）のたびに push する**（2026-10-31 ユーザー決定） |
| ブランチの掃除 | **実装管理担当** | 下記「掃除」 |

#### ブランチ

- 命名は **`<種別>/<主題>`**。種別は `feat` / `fix` / `docs` / `tune` / `chore` / `test`。
  作業パケット単位なら記号を入れる（例: `feat/wp-base-01-skeleton`）。
- **1 作業パケット ＝ 1 ブランチ。**複数のパケットを 1 本に混ぜない
  （混ぜると片方だけ差し戻せない。`git add -p` が使えない環境なので後から分割もできない）。
- **文書だけの修正は `main` へ直接コミットしてよい。**コードを含むものは必ずブランチを切る。
- **並行させるときは片方を `git worktree` に隔離する**（§2.1）。同じファイルを 2 体が触ると衝突する。

#### マージ

- **`--no-ff` でマージする。**作業の単位が履歴に残る。
- **squash しない。**`EXCEPTION-LEDGER.md` や設計文書がコミットハッシュを名指しで参照するため、
  潰すと追跡が切れる。
- マージコミットの本文に**検証の結果を数字で書く**（例: pytest 910 passed、e2e 208 passed）。
  後から「何を根拠にマージしたか」を追えるようにする。

#### 計画書を都度更新する

**この計画書は、証拠が動いたその作業の区切りで更新する。まとめて後で直さない。**
th-system では 14 回マージしたのに計画書に反映されたのは 1 行だけで、
「次に何をやるか」を聞かれて完了済みの項目を答えかけた（th-system 2026-09-23）。

| いつ | 何を直すか |
| --- | --- |
| `main` へマージした直後 | そのパケットの §4 の状態列、§6 の該当行（済みなら取り消し線＋コミット）、§3 の段階の状態・「いま分かっている危険」 |
| マージして「配線済み・実機未確認」になったとき | 上に加えて、**`docs/試験項目.md` の貯め置きの節に 1 行足す**（確かめること・合格の目安・出どころ）。実機で確かめたらその行を消す |
| 実機確認を記録したとき（試験記録 ／ `Spec-open.md` への「確認済み」の追記） | 同上。証拠の水準（§1）を「配線済み」→「実機確認済み」へ上げる |
| 台帳（`EXCEPTION-LEDGER.md`）の状態を変えたとき | 台帳 ID を併記している §4・§6 の行 |

- 文書だけの更新なので `main` へ直接コミットしてよい。マージと同じ区切りで、**別コミット**にする。
- 直したら §1 の「最終同期」の日付を更新する。
- **§6 から次の作業を選ぶ前に**、`git log --merges --since=<最終同期日> main` と突き合わせる。
  食い違っていたら、選ぶ前に計画書を直す。

#### コミットメッセージ

`<種別>(<範囲>): <日本語の 1 行>` ＋ 本文に**何をなぜ**（どう直したかは差分を見れば分かる）。
末尾の帰属行は会話の指示に従う。

#### 掃除

- **マージしたブランチはその場で消す**（ローカル・`origin` とも）。溜めない。
- **放置されたブランチは四半期ごとに棚卸しする。**`main` が大きく動いたあとは、古いブランチの
  土台が古すぎて rebase より作り直しが速いことが多い。
- 消したブランチの SHA は、棚卸しのコミットメッセージに残す（`git branch <name> <sha>` で復元できるように）。

#### 長期保管するブランチ（`main` には統合しない）

いまは無い。展示用など、本来の機能ではないが残したいものができたらここに載せる（掃除の対象外になる）。

#### `CLAUDE.md` と重複させない

作業前の `git status` 確認、自分が変更したファイルだけをステージする、`git add -A` を使わない、
`git add -p` が使えないので 1 ファイルに複数の関心事を混ぜない ── これらは
`CLAUDE.md`「作業開始前のルール」が正。ここには書かない。

| --- | --- |

### いま分かっている危険

| 危険 | 出どころ |
